## 第一部分 · 选题背景与意义

### 1.1 选题背景

检索增强生成(Retrieval-Augmented Generation, RAG)是当前大语言模型(LLM)应用最广泛的范式之一。其核心思想是:在生成阶段,从外部知识库中检索与问题相关的文档片段,与用户问题一同输入 LLM,从而缓解模型的幻觉问题、知识时效性问题和领域适配问题。

**然而,标准的 RAG 范式存在一个根本性假设——"一次检索就够用"。**

在多跳问答(Multi-hop QA)、复杂推理、事实核查等任务中,问题的答案往往需要**跨多个文档、经过多步推理**才能得出。例如:"二战期间,创立苹果公司的两位创始人中,谁在 1955 年出生于美国哪个州?"这个问题需要:
1. 检索"苹果公司创始人" → 得到 Steve Jobs / Steve Wozniak
2. 检索"二战期间出生于美国" → 得到对应州
3. 跨文档推理:Jobsb出生于加利福尼亚州

**标准 RAG 在这种任务上的失败模式已经被多项研究指出**:

- **检索失败**:一次检索返回的 Top-K 文档不包含所有必要事实
- **推理失败**:即使检索到所有事实,模型也难以在长上下文中正确整合
- **幻觉问题**:模型倾向于"猜测"而非"再查一次"

**Agentic RAG(智能体驱动的 RAG)**正是为了解决这些问题而提出的新范式:让 LLM Agent **主动决定何时检索、检索什么、检索几次**,而非被动地接受单次检索结果。

### 1.2 选题意义

#### 1.2.1 理论意义

- 填补"单次检索 vs 迭代检索"决策机制的**系统性研究空白**。
- 揭示 Agent **检索决策行为**与最终答案质量之间的关系。
- 提出可复现的**"决策质量评估协议"**,为 Agentic RAG 后续研究提供方法论。

#### 1.2.2 实践意义

- 为多跳问答、事实核查、企业知识库问答等场景提供更鲁棒的 RAG 方案。
- 与已有 RAG 项目形成**复用 + 演进**关系:基础 RAG 模块复用,新增 Agent 决策层。
- 提供"何时需要 Agent 决策、何时单次检索就够"的**实践指导原则**。

#### 1.2.3 与已有 RAG 项目的互补性

- 已有项目研究"如何优化检索效果",本项目研究"如何决策检索时机"。
- 已有项目以单文档 FAQ 为主,本项目以**多文档多跳问答**为主。
- 已有项目偏工程消融,本项目偏**机制研究与行为分析**。
- 工程上:已有项目的 `vector_store.py`、`reranker.py`、`embedding.py` 可直接复用为新项目的"基础检索器"。

## 第二部分 · 国内外研究现状

### 2.1 从 RAG 到 Agentic RAG 的演进

| 阶段 | 代表工作 | 提出时间 | 核心思想 |
|------|---------|---------|---------|
| **朴素 RAG** | Lewis et al. 2020 | 2020 | DPR + BART 生成,单次检索 |
| **Self-RAG** | Asai et al. 2023 | 2023 | 模型自评检索质量,动态决定是否检索 |
| **FLARE** | Jiang et al. 2023 | 2023 | 生成过程中检测不确定性,触发二次检索 |
| **IRCoT** | Trivedi et al. 2023 | 2023 | 思维链引导的迭代检索 |
| **ReAct** | Yao et al. 2023 | 2022.10 | 通用 Agent 范式,可用于多跳问答 |
| **Self-Ask** | Press et al. 2023 | 2023 | 让模型"自己问自己",引导中间问题 |
| **ReAct + RAG** | 多家 | 2023-2024 | 把 ReAct 的 Action 设为"检索"操作 |
| **Agentic RAG 综述** | 多篇 | 2024-2025 | 系统化命名"Agentic RAG"概念 |
| **Multi-Agent RAG** | 多家 | 2024 | 多个 Agent 协作完成检索与生成 |

### 2.2 现有研究的不足

通过阅读 Self-RAG、FLARE、IRCoT、ReAct、Self-Ask 等代表性工作,可归纳出:

1. **决策机制不透明**。多数工作仅展示"Agent 决策了",但不分析"为什么这样决策"。
2. **决策质量缺乏量化评估**。研究只报告最终 EM/F1,不评估决策本身的对错。
3. **检索步数与准确率的权衡不明**。多步检索必然更准,但延迟也更高;何时"够用"不清楚。
4. **任务类型与决策策略的适配性研究稀缺**。数学、问答、推理等任务可能需要不同决策模式。
5. **小模型在 Agentic RAG 上的能力未充分研究**。现有工作主要在 GPT-4 上。

### 2.3 本选题的切入点

围绕上述空白,本选题聚焦以下研究切口:

1. **决策行为可视化与分析**:Agent 在多跳问答任务中究竟"在查什么、什么时候查",做系统分析
2. **决策质量评估协议**:定义"决策正确率",与最终答案正确率解耦
3. **检索步数-准确率 Pareto 前沿**:研究"何时停止检索"的边际效益
4. **多种决策策略的对比**:ReAct、Plan-and-Execute、Self-Ask、IRCoT 等范式在多跳问答上的对比
5. **基于已有 RAG 项目的扩展**:把现有基础 RAG 升级为 Agentic RAG,做"前 vs 后"对比

## 第三部分 · 研究内容与目标

### 3.1 核心研究问题

**主问题**:在多跳问答任务中,LLM Agent 能否学会"何时检索、检索什么、检索几次",以最少的检索步数获得最高的答案准确率?

**子问题**:

- **Q1(决策问题)**:Agent 在多跳问答中的检索决策(何时检索 / 检索什么)与最终答案正确率有何关系?
- **Q2(范式问题)**:不同 Agent 范式(ReAct / Plan-and-Execute / Self-Ask / IRCoT)对检索决策行为有何影响?
- **Q3(效率问题)**:检索步数与答案准确率之间是否存在 Pareto 前沿?最优停止时机如何确定?
- **Q4(对比问题)**:Agentic RAG 与已有项目中的单次 RAG(基础对照)相比,在多跳问答任务上的提升有多大?成本(步数 / 延迟)如何?

### 3.2 研究内容

围绕上述问题,本研究拟开展以下五部分工作:

1. **多跳问答评估基准构建**。基于 HotpotQA / 2WikiMultihopQA / MuSiQue 构建统一评估基准,继承已有项目的工程基础设施。
2. **Agent 决策行为记录与分析框架**。完整记录每次 Agent 推理的 Thought / Action / Observation,支持决策行为可视化与统计。
3. **多种 Agent 范式的对比实验**。ReAct / Plan-and-Execute / Self-Ask / IRCoT 四种范式在多跳问答上的系统对比。
4. **Agentic RAG vs 基础 RAG 对比实验**。把已有项目的"单次检索 RAG"作为基础对照,对比 Agentic RAG 的提升与成本。
5. **决策质量评估协议**。定义并验证"检索决策正确率"指标,作为最终答案正确率的补充。

### 3.3 研究目标

- **学术目标**:撰写一篇可投稿至 ACL / EMNLP / NLPCC / CCL 等会议的论文。
- **工程目标**:交付一个完整、可复现的 Agentic RAG 实验平台,代码风格与已有 RAG 项目一致。
- **个人目标**:在 RAG / Agent / 决策机制方向积累完整研究经验。

### 3.4 创新点

1. **首次系统对比多种 Agentic RAG 范式在多跳问答上的决策行为与效果**,填补现有文献的横向对比空白。
2. **提出"检索决策正确率"指标**,将决策质量从最终结果中解耦。
4. **系统揭示检索步数-准确率 Pareto 前沿**,为"何时停止检索"提供经验依据。
5. **基于已有 RAG 项目的扩展式研究**,形成"基础 RAG → Agentic RAG"的演进证据链。

### 4.3 Agent 范式设计要点

#### 4.3.1 ReAct(基线 Agent 范式)
- 多轮循环:`Thought → Action → Observation`
- 动作集:`Search(query)` / `Lookup(term)` / `Finish(answer)`
- 终止条件:模型输出 `Finish(answer)` 或达到最大步数(默认 8 步)

#### 4.3.2 Plan-and-Execute
- 阶段一:**规划**——生成"我需要查 A、B、C 才能回答"
- 阶段二:**执行**——逐步检索,每步验证是否需要补充检索
- 适合"长视野规划能力"对比

#### 4.3.3 Self-Ask
- 提示模型"在回答之前先问自己中间问题"
- 每个中间问题触发一次检索
- 适合"显式中间推理"对比

#### 4.3.4 IRCoT(Interleaving Retrieval with CoT)
- 在思维链的每一步中**自动检测**是否需要检索
- 检索 query 从当前推理步骤中自动抽取
- 适合"细粒度决策"对比

### 4.4 基础检索器(复用已有项目)

直接复用 `rag-research-project/src/` 中的:
- `embedding.py` → `src/llm/local_model.py` 中的 Embedding 加载
- `vector_store.py` → `src/retrievers/faiss_retriever.py`
- `reranker.py` → `src/retrievers/rerank_retriever.py`

新项目不重新实现检索部分,**专注于决策层**。

### 4.5 模型选型

| 模型 | 用途 | 推荐档位 |
|------|------|---------|
| Qwen2.5-3B-Instruct | 默认 Agent 模型 | 主力 |
| Qwen2.5-7B-Instruct | 上限对比 | 可选 |
| Qwen2.5-1.5B-Instruct | 小模型下界 | 可选 |

> 重点不在"模型规模对比",而在"决策行为对比",所以不需要 0.5B-7B 全谱。3B 为主,1.5B 和 7B 各一组做下界/上界验证即可。

## 第五部分 · 实验设计

### 5.1 实验变量

#### 自变量
- **Agent 范式**:ReAct / Plan-and-Execute / Self-Ask / IRCoT(4 种)
- **检索器类型**:FAISS only / FAISS + Reranker(2 种,复用已有项目)
- **最大检索步数**:3 / 5 / 8 / 10(用于 Pareto 分析)

#### 因变量
- **答案指标**:EM、Answer F1、Support F1(HotpotQA 特有)
- **决策指标**:**检索决策正确率**(新增)、过度检索率、检索不足率
- **效率指标**:平均检索步数、token 消耗、延迟
- **成本指标**:检索次数、检索 query 长度

#### 控制变量
- 检索语料:HotpotQA 全量文档
- 评估集:dev / test 固定划分
- 模型:Qwen2.5-3B-Instruct 为主
- 推理参数:`temperature=0`(贪心解码)
- 提示词模板:每个范式固定

### 5.2 主对比实验

#### 对照组
- **基线 1:无 RAG**——直接生成
- **基线 2:单次 RAG**——已有项目的标准 RAG
- **基线 3:CoT + 单次 RAG**——思维链 + 单次检索

#### 实验组(Agentic RAG × 范式)
4 范式 × 2 检索器 × 4 步数上限 = **32 组实验**

每组 500-1000 样本(基于 HotpotQA dev)。

### 5.3 消融实验

- 移除反思(IRCoT → 单次 RAG)
- 移除检索步骤上限的影响
- 检索 Top-K 的影响(1 / 3 / 5 / 10)
- 不同提示词模板的鲁棒性

### 5.4 评估指标详解

#### 答案指标(继承 HotpotQA 官方)
- **EM**(Exact Match):答案完全匹配
- **Answer F1**:答案 F1
- **Support F1**:支撑事实 F1(HotpotQA 特有)

#### 决策指标(本研究新增)
- **检索决策正确率**:Agent 决定"检索" vs "不检索"是否正确(基于 oracle 判断)
- **检索时机准确率**:在需要检索时决定检索、在不需要时不检索的比例
- **检索 query 相关性**:每次检索的 query 与真实需要的事实的匹配度

#### 效率指标
- **平均检索步数**
- **检索步数-准确率 Pareto 曲线**
- **每任务的 token 消耗**
- **每任务的延迟**

### 5.5 决策行为可视化

- **轨迹时间线**:每个样本的 Thought → Action → Observation 时间线
- **决策热力图**:不同任务难度下的"何时检索"决策热力图
- **检索步数分布**:不同范式的检索步数直方图
- **失败模式分布饼图**:规划失败 / 检索失败 / 推理失败 / 决策失败

## 第六部分 · 数据集调研与准备

### 6.1 推荐数据集

| 数据集 | 任务类型 | 规模 | 难度 | 推荐度 | 备注 |
|--------|---------|------|------|--------|------|
| **HotpotQA** | 多跳问答 | 113K | 中 | ⭐⭐⭐ | 经典多跳,带支撑事实标注 |
| **2WikiMultihopQA** | 多跳问答 | 192K | 中 | ⭐⭐⭐ | 2 跳推理,质量更稳定 |
| **MuSiQue** | 多跳问答 | 25K | 中高 | ⭐⭐⭐ | 推理路径清晰,可控性强 |

### 10.2 各章节写作要点

#### 选题背景
- 从"标准 RAG 的局限"切入(单次检索不足)
- 引出"多跳问答的挑战"
- 提出"Agentic RAG"作为解决方案
- 引用 2-3 个代表性工作(Self-RAG、IRCoT、FLARE)

#### 研究现状
- 按"从 RAG 到 Agentic RAG 的演进"组织
- 重点批评现有工作的"决策机制不透明"问题
- 引用至少 12 篇相关文献

#### 研究内容
- 用"主问题 + 子问题"形式清晰表述
- 强调"决策行为研究"是核心

#### 技术路线
- 提供整体流程图(参考 4.1 节)
- 模块划分要体现"决策层 + 检索层"分离

### 10.3 答辩常见问题预演

- Q:"和已有 RAG 项目的区别?"
  A:"已有项目研究如何让检索更准,新项目研究何时该再检索一次。"

  A:"本地化部署与成本是研究动机之一,本研究在小模型上验证。"
- Q:"决策正确率怎么定义?"
  A:"用 oracle 判断:如果检索了必要的事实则算正确,过度检索有惩罚。"
